# Auto-fix

`migrationpilot analyze <file> --fix` rewrites the migration in place, fixing
what can be fixed without changing what the migration means. 20 rules qualify;
the rest either need a multi-step plan or a human. Add `--dry-run` to see the
diff without writing.

```bash
migrationpilot analyze migrations/003_add_index.sql --fix --dry-run
migrationpilot analyze migrations/003_add_index.sql --fix
```

## What counts as auto-fixable

Every rule falls into one of three buckets.

**MECHANICAL** — one deterministic edit to one statement (or to the transaction
wrapper around it) that cannot change what the migration does. `--fix` applies
these. The bar is deliberately high: `MP038` (INT → BIGINT) is mechanical only
because the rule fires on `CREATE TABLE`, where no rows exist yet. The identical
edit on a live column rewrites the whole table, so that case is not fixed at all.

**PLAN-ONLY** — the safe fix is a choreography: several statements in a fixed
order, sometimes with an application release between them. `--fix` never touches
these. `migrationpilot plan-fix` writes the plan instead — see
[plan-fix.md](plan-fix.md).

**UNFIXABLE** — the safe path depends on something MigrationPilot cannot know:
intent, data shape, or release schedule. You get the violation and a safe
alternative to apply yourself.

`migrationpilot list-rules` marks each rule `[auto-fix]` or `[plan-fix]`, and
`migrationpilot explain MP005` shows which bucket one rule is in.

### Choices worth knowing about

**MP074 emits `DEFERRABLE INITIALLY IMMEDIATE`, not `INITIALLY DEFERRED`.**
The rule's example shows `INITIALLY DEFERRED`, which moves every foreign-key
error from the failing statement to `COMMIT`. That is a real behaviour change,
so `--fix` will not make it for you. `INITIALLY IMMEDIATE` keeps the check
timing exactly as it was while letting a bulk load opt in with
`SET CONSTRAINTS ... DEFERRED`. Change it to `DEFERRED` yourself if that is what
you want.

**MP039 emits `GENERATED BY DEFAULT AS IDENTITY`, not `GENERATED ALWAYS`.**
`SERIAL` lets you insert an explicit id and so does `BY DEFAULT`; `ALWAYS`
rejects it. The identity sequence keeps the same `table_column_seq` name
`SERIAL` would have produced, so existing `setval()` calls keep working.

**MP005 and MP030 add `NOT VALID` but not the `VALIDATE CONSTRAINT` that
follows.** A constraint that fails validation needs the offending rows dealt
with first, which is not something a rewrite can decide. Run `plan-fix` to get
both steps.

**MP042 only names indexes it can name exactly.** It writes the name PostgreSQL
would have generated itself (`users_email_idx`), so nothing about the resulting
index changes. Expression indexes are left alone: PostgreSQL names those
`<table>_expr_idx` with a collision counter that cannot be reproduced from the
file. `MP023` also stands down in that case, because
`CREATE INDEX CONCURRENTLY IF NOT EXISTS ON t (...)` has no name to attach the
clause to and would not parse.

**MP012 and MP025 only lift a statement out of a transaction when it is the
first, last, or only statement in the block.** Those three positions keep every
statement in its original order. A statement in the middle would split the block
in two, changing which statements are atomic with which — that is left to you.

**MP074 only rewrites the `ALTER TABLE` form.** An inline foreign key inside
`CREATE TABLE` needs the clause attached to one specific column definition, so
it is reported rather than rewritten.

## How the rewrite works

The fixer splits the file into statements with its own lexer (`src/fixer/statements.ts`),
which tracks string literals, quoted identifiers, dollar-quoted bodies, and
comments so that only a real top-level `;` ends a statement. Fixes then apply to
whole statements, which is why a four-line `ADD CONSTRAINT ... FOREIGN KEY` gets
its `NOT VALID` in the right place.

Whitespace, comments, and indentation between statements are preserved
byte-for-byte. A file with nothing to fix comes back identical.

When several fixes land on one statement they run in a fixed order, because two
pairs interact: `MP042` names an index before `MP001`/`MP023` insert keywords in
front of `ON`, and `MP074`'s `DEFERRABLE` goes in before `MP005` appends the
trailing `NOT VALID` that PostgreSQL's grammar requires to come last.

One pass fixes what the analysis found. A fix can occasionally reveal a further
suggestion — `serial` becomes `INTEGER GENERATED BY DEFAULT AS IDENTITY`, which
`MP038` would then rather see as `BIGINT` — so re-run until the file is clean.

## Reading the output

```
Fixed 18 violation(s) in migrations/003_add_index.sql
5 violation(s) require manual fixes:
  - MP016: FK constraint "fk_orders_user" on "orders"(user_id) → "users" has no matching index...
2 violation(s) need a multi-step plan (MP002, MP007).
  Run: migrationpilot plan-fix migrations/003_add_index.sql
```

Leftovers are split in two: the ones a human has to think about, and the ones
`plan-fix` has a plan for.
