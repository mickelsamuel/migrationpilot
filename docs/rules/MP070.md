# MP070: warn-concurrent-index-invalid

**Severity**: Warning | **Auto-fixable**: No | **Tier**: Free

## What It Detects
CREATE INDEX CONCURRENTLY without a preceding DROP INDEX IF EXISTS for the same index name.

## Why It's Dangerous
CREATE INDEX CONCURRENTLY can fail partway through (due to deadlock, unique violation, or cancellation), leaving behind an invalid index. Invalid indexes are not used by the query planner but still consume disk space and slow down writes. Retrying the CREATE INDEX CONCURRENTLY without first dropping the invalid index will fail with "relation already exists." Adding DROP INDEX IF EXISTS before the retry ensures a clean slate and makes the migration idempotent.

## Bad Example
```sql
CREATE INDEX CONCURRENTLY idx_email ON users (email);
-- If this fails, leaves an invalid index behind
-- Retrying will fail with "relation already exists"
```

## Good Example
```sql
-- Drop any leftover invalid index from a previous failed attempt
DROP INDEX CONCURRENTLY IF EXISTS idx_email;
CREATE INDEX CONCURRENTLY idx_email ON users (email);
```

## The Exception: An Index a Constraint Owns
Drop-first is the right convention for an ordinary index. It is not available for one a
`UNIQUE` or `PRIMARY KEY` constraint owns, because PostgreSQL refuses that drop outright:

```
ERROR: cannot drop index users_email_key because constraint users_email_key on table users requires it
```

Neither `IF EXISTS` nor `CONCURRENTLY` softens it — all three forms fail identically,
verified on PostgreSQL 18.3. The repair path there is to rebuild in place, or to drop the
constraint first:

```sql
REINDEX INDEX CONCURRENTLY users_email_key;
```

So the rule stands down when the index is already owned by a constraint on the target
database, or when the migration itself hands it to one further down the file — the
[MPH-009](../handbook/09-unique-constraint-scan.md) pattern:

```sql
CREATE UNIQUE INDEX CONCURRENTLY users_email_key ON users (email);
ALTER TABLE users ADD CONSTRAINT users_email_key UNIQUE USING INDEX users_email_key;
-- No DROP INDEX ahead of the build: from the ADD CONSTRAINT onward, it would be rejected.
```

Ownership is read from `pg_constraint.conindid` when a database connection is available and
from the `ADD CONSTRAINT` statements in the file otherwise. A unique index is not the same
object as a unique constraint, and the index's name says nothing about which one it is —
see [MP097](./MP097.md).

## Auto-fix
This rule is not auto-fixable. Add `DROP INDEX CONCURRENTLY IF EXISTS` before
`CREATE INDEX CONCURRENTLY` to handle failed retries, unless a constraint owns the index, in
which case use `REINDEX INDEX CONCURRENTLY`. Check for invalid indexes with:
`SELECT indexrelid::regclass FROM pg_index WHERE NOT indisvalid`.
