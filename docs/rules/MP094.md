# MP094: require-attach-partition-check

**Severity**: Warning | **Auto-fixable**: No | **Tier**: Free

## What It Detects
`ALTER TABLE ... ATTACH PARTITION` where the migration does not add a `CHECK` constraint to the incoming table beforehand. A `CHECK` added earlier in the same file — via `ALTER TABLE ... ADD CONSTRAINT` or inline in the table's `CREATE TABLE` — satisfies the rule, so a correctly written attach produces no violation.

## Why It's Dangerous
`ATTACH PARTITION` is meant to be a catalog operation, and mostly it is. The exception is validation: PostgreSQL has to prove that every row in the incoming table satisfies the partition bound, and by default it proves it by reading all of them. That scan runs while holding `ACCESS EXCLUSIVE` on both the incoming table and the parent, which means the entire partitioned table — every partition, not just the new one — is unavailable for the duration.

The table being attached is usually a freshly built one with millions of rows, so this is minutes of downtime for an operation that reads like metadata bookkeeping.

PostgreSQL will skip the scan entirely if an existing `CHECK` constraint already implies the partition bound. The work does not disappear, it moves: validating the `CHECK` takes `SHARE UPDATE EXCLUSIVE`, which does not block reads or writes, and can be done well before the attach. The `ATTACH` itself then becomes the catalog-only operation it was supposed to be.

The constraint is redundant once the partition is attached — the partition bound enforces the same thing — so it can be dropped afterwards.

## Bad Example
```sql
ALTER TABLE events ATTACH PARTITION events_2026_01
  FOR VALUES FROM ('2026-01-01') TO ('2026-02-01');
-- Full scan of events_2026_01, ACCESS EXCLUSIVE on the whole hierarchy
```

## Good Example
```sql
-- 1. Add a CHECK matching the bound, without validating it yet
ALTER TABLE events_2026_01
  ADD CONSTRAINT events_2026_01_bound
  CHECK (ts >= '2026-01-01' AND ts < '2026-02-01') NOT VALID;

-- 2. Validate it under a lock that lets traffic through
ALTER TABLE events_2026_01 VALIDATE CONSTRAINT events_2026_01_bound;

-- 3. The attach is now catalog-only
ALTER TABLE events ATTACH PARTITION events_2026_01
  FOR VALUES FROM ('2026-01-01') TO ('2026-02-01');

-- 4. Optional: the partition bound now enforces this
ALTER TABLE events_2026_01 DROP CONSTRAINT events_2026_01_bound;
```

The `CHECK` must cover the bound exactly, including the half-open interval — `>= lower AND < upper`. If it is narrower than the bound PostgreSQL still scans, and it must not be `NOT VALID` at attach time or it cannot be trusted.

## Auto-fix
This rule is not auto-fixable. The constraint has to name the partition key column and reproduce the bound, and getting the boundary conditions wrong silently reinstates the scan the rule was trying to avoid.
