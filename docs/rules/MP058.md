# MP058: multi-alter-table-same-table

**Severity**: Warning | **Auto-fixable**: No | **Tier**: Free

## What It Detects
Two or more `ALTER TABLE` statements on the same table, in the same transaction block,
where merging them into one statement costs nothing.

## Why It's Dangerous
Each `ALTER TABLE` acquires `ACCESS EXCLUSIVE` independently. Multiple separate statements
mean multiple lock/unlock cycles, each going through the lock queue, and each able to stall
behind a long-running query — and while one waits, every reader arriving after it queues
behind the waiter. Combining subcommands into a single `ALTER TABLE` reduces the blocking
window from N lock cycles to one.

## Bad Example
```sql
ALTER TABLE users ADD COLUMN bio text;
ALTER TABLE users ADD COLUMN avatar text;
ALTER TABLE users ALTER COLUMN bio SET DEFAULT '';
-- 3 separate lock acquisitions
```

## Good Example
```sql
ALTER TABLE users
  ADD COLUMN bio text DEFAULT '',
  ADD COLUMN avatar text;
-- 1 lock acquisition
```

## When It Does Not Fire
Some migrations split `ALTER TABLE` on purpose, and merging them would put back the work
they were written to avoid. The rule stays quiet on all of these.

**A `NOT VALID` constraint and its `VALIDATE`** ([MPH-004](../handbook/04-check-then-not-null.md)).
`VALIDATE CONSTRAINT` on its own takes `SHARE UPDATE EXCLUSIVE`, so writes continue through
the scan. Merged into a statement with any other subcommand, the scan runs under that
statement's `ACCESS EXCLUSIVE` instead and blocks everything. On PostgreSQL 18.3 the split
form reports `ShareUpdateExclusiveLock` in `pg_locks` and the merged form reports
`AccessExclusiveLock`.

```sql
ALTER TABLE orders ADD CONSTRAINT orders_amount_positive CHECK (amount > 0) NOT VALID;
ALTER TABLE orders VALIDATE CONSTRAINT orders_amount_positive;   -- keep these apart
```

**`SET NOT NULL` and the `CHECK` that proves it** ([MPH-003](../handbook/03-set-not-null-full-scan.md)).
The scan is skipped only while the valid `CHECK` survives the command — the ALTER TABLE
manual requires that it "is not dropped in the same command". Merging the `DROP CONSTRAINT`
in reinstates the full scan: on 18.3, `seq_scan` on the table goes from 1 to 2.

```sql
ALTER TABLE orders ALTER COLUMN customer_id SET NOT NULL;
ALTER TABLE orders DROP CONSTRAINT orders_customer_id_not_null;  -- separate command
```

**Anything reading or writing the table in between.** Merging two `ALTER`s across a
`UPDATE users SET ...` would move a statement past it, which is a different migration.

**`ALTER`s in different transaction blocks.** There is a `COMMIT` between them; they cannot
be merged without removing it.

## Auto-fix
This rule is not auto-fixable. Merging subcommands can change the order in which they are
applied, and the safe alternative is a suggestion to read rather than a rewrite to apply.
