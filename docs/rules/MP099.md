# MP099: warn-security-definer-search-path

**Severity**: Critical | **Auto-fixable**: No | **Tier**: Free

## What It Detects
`CREATE FUNCTION` or `CREATE PROCEDURE` declared `SECURITY DEFINER` without a `SET search_path` clause. An explicit `SECURITY INVOKER` is not flagged, and neither is a function that pins `search_path`. An unrelated `SET` clause — `SET work_mem`, say — does not count as pinning it.

## Why It's Dangerous
`SECURITY DEFINER` runs the function body with the privileges of the function's owner rather than the caller's. That is the whole point of it, and it is why the body has to be careful about what its names refer to.

`search_path` decides what every unqualified name in that body resolves to. Leave it unpinned and the caller supplies it — and the caller is precisely the person who does not have the owner's privileges. The attack is direct:

```sql
CREATE SCHEMA evil;
CREATE TABLE evil.users (id int, role text);
SET search_path = evil, public;
SELECT admin_only_function();
-- The body's unqualified "users" resolves to evil.users,
-- and operates on it with the owner's privileges
```

The same trick works on functions and operators, not just tables, so even a body that only does arithmetic can be subverted by shadowing an operator it uses.

If the function is owned by a superuser or by the schema owner, this is privilege escalation available to anyone who can call it — and `EXECUTE` on new functions is granted to `PUBLIC` by default, so that is usually everyone.

PostgreSQL accepts the unpinned form without a warning. Nothing surfaces at creation time, nothing surfaces in testing, and by the time anyone looks the function is deployed and callable. This is the single most common finding in PostgreSQL security reviews, which is why it belongs in migration review rather than in an audit six months later.

## Bad Example
```sql
CREATE FUNCTION promote_user(uid int) RETURNS void AS $$
  UPDATE users SET role = 'admin' WHERE id = uid;
$$ LANGUAGE sql SECURITY DEFINER;
-- Caller decides which "users" this writes to
```

## Good Example
```sql
CREATE FUNCTION promote_user(uid int) RETURNS void AS $$
  UPDATE public.users SET role = 'admin' WHERE id = uid;
$$ LANGUAGE sql
  SECURITY DEFINER
  SET search_path = pg_catalog, public;

-- EXECUTE is granted to PUBLIC by default — take it back
REVOKE EXECUTE ON FUNCTION promote_user FROM PUBLIC;
GRANT EXECUTE ON FUNCTION promote_user TO app_role;
```

The `SET search_path` clause is the guarantee; schema-qualifying names inside the body is belt and braces and worth doing as well. Putting `pg_catalog` first also prevents shadowing of built-in functions and operators.

## Auto-fix
This rule is not auto-fixable. The correct `search_path` depends on which schemas the body legitimately needs, and guessing it wrong turns a security problem into a runtime failure.

Audit what already exists:

```sql
SELECT n.nspname, p.proname, p.proconfig
FROM pg_proc p JOIN pg_namespace n ON p.pronamespace = n.oid
WHERE p.prosecdef AND (p.proconfig IS NULL
  OR NOT EXISTS (SELECT 1 FROM unnest(p.proconfig) c WHERE c LIKE 'search\_path=%'));
```
