# MP090: warn-trigger-on-hot-table

**Severity**: Warning | **Auto-fixable**: No | **Tier**: Free

## What It Detects
`CREATE TRIGGER ... FOR EACH ROW`. Statement-level triggers are not flagged — they fire once per statement rather than once per row, and a trigger that omits `FOR EACH ROW` is statement-level by default.

## Why It's Dangerous
There are two costs, and the small one is the one people think about.

Creating the trigger takes a `SHARE ROW EXCLUSIVE` lock. Reads continue, writes queue. That is usually brief, though on a busy table it can queue behind an existing long transaction and take the write traffic with it while it waits.

The cost that lasts is the trigger body. A row-level trigger runs once per affected row, inside the transaction doing the writing, so from this migration onward the function is on the critical path of every `INSERT`, `UPDATE` or `DELETE` on the table. A function that takes a millisecond is invisible on single-row writes and adds ten seconds to a 10,000-row `UPDATE` — ten seconds of extra lock-holding, not just extra runtime. Anything the trigger writes to becomes part of that transaction too, so an audit table written by a trigger is now a source of lock contention for the table being audited, and an error inside the trigger rolls back the original write.

None of this is visible in the migration. The `CREATE TRIGGER` is one line; the cost is distributed across every write the application makes afterwards.

## Bad Example
```sql
CREATE TRIGGER audit_users
  AFTER INSERT OR UPDATE OR DELETE ON users
  FOR EACH ROW EXECUTE FUNCTION write_audit_log();
-- Now part of every write to users, forever
```

## Good Example
```sql
-- Bound the wait so trigger creation cannot stall writes behind a long transaction
SET lock_timeout = '5s';
CREATE TRIGGER audit_users
  AFTER INSERT OR UPDATE OR DELETE ON users
  FOR EACH ROW EXECUTE FUNCTION write_audit_log();
RESET lock_timeout;
```

If the trigger only needs to see the change as a whole, a statement-level trigger with transition tables does the same work once instead of once per row:

```sql
CREATE TRIGGER audit_users
  AFTER UPDATE ON users
  REFERENCING NEW TABLE AS changed
  FOR EACH STATEMENT EXECUTE FUNCTION write_audit_log();
```

## When It Does Not Fire
The sync trigger of an expand/contract migration is exempt. When a migration adds a column
to a table and then puts a row-level trigger on that same table to keep the new column in
step with the old one, the trigger is not incidental overhead — it is what lets old and new
application code write the table at the same time, and the contract step drops it. Warning
about the per-write cost of the thing that prevents the outage points the wrong way, and
both [MPH-007](../handbook/07-alter-column-type-rewrite.md) and
[MPH-015](../handbook/15-rename-breakage.md) prescribe it.

Three things have to line up, all of them visible in the migration:

1. The same file adds a column to the table the trigger is on, before the trigger.
2. The trigger fires on `INSERT` and `UPDATE` — what a sync trigger has to do.
3. Either the trigger's function is defined in this migration and mentions the added
   column, or the migration backfills that column afterwards.

```sql
ALTER TABLE users ADD COLUMN email_address text;

CREATE OR REPLACE FUNCTION users_sync_email() RETURNS trigger AS $$
BEGIN
  NEW.email_address := COALESCE(NEW.email_address, NEW.email);
  RETURN NEW;
END $$ LANGUAGE plpgsql;

CREATE TRIGGER users_sync_email
  BEFORE INSERT OR UPDATE ON users
  FOR EACH ROW EXECUTE FUNCTION users_sync_email();
-- Not reported: this is the expand step of an expand/contract migration.
```

A trigger on a table the migration never expanded, one whose function comes from somewhere
else, and a `DELETE`-only audit trigger match none of this and are still reported.

## Auto-fix
This rule is not auto-fixable. Whether a trigger can be statement-level depends on what its function does with `NEW` and `OLD`, and rewriting it is a change to application behaviour rather than to the migration.
