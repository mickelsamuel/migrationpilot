# MP088: require-analyze-after-backfill

**Severity**: Warning | **Auto-fixable**: No | **Tier**: Free

## What It Detects
A bulk `UPDATE` or `INSERT ... SELECT` with no `ANALYZE` covering the same table later in the file. `INSERT ... VALUES` is treated as seeding rather than a backfill and is not flagged. A bare `ANALYZE`, a targeted `ANALYZE table`, or a `VACUUM ANALYZE table` all satisfy the rule. One violation is reported per table, on the last backfill that touches it.

## Why It's Dangerous
The planner does not look at your data. It looks at `pg_statistic` — the null fraction, the distinct count, the histogram — and picks a plan from those numbers. A backfill can invalidate all of them at once. A column that was 100% NULL before the `UPDATE` is now fully populated, but the statistics still say it is empty, so the planner keeps choosing plans built for a table that no longer exists: a sequential scan over a column that is now highly selective, a nested loop sized for a row count that is off by orders of magnitude.

Autovacuum fixes this eventually. The catch is *eventually*: it triggers on a row-change threshold (`autovacuum_analyze_scale_factor`, 10% of the table by default), not on your migration finishing. On a large table with a partial backfill the threshold may not be crossed for hours, and on a table that is already busy the autovacuum worker competes with everything else.

The failure mode is the awkward kind. The migration reports success, the deploy goes green, and query latency degrades sometime afterwards with nothing obviously connecting the two. `ANALYZE` takes a `ShareUpdateExclusiveLock`, which does not block reads or writes, and samples rather than scanning — it costs a fraction of what the backfill just cost.

## Bad Example
```sql
UPDATE users SET status = 'active' WHERE status IS NULL;
-- Migration ends here. Planner still thinks status is entirely NULL.
```

## Good Example
```sql
UPDATE users SET status = 'active' WHERE status IS NULL;
ANALYZE users;
```

Batched backfills want the `ANALYZE` after the last batch, not inside the loop:

```sql
-- batch 1..N run separately
ANALYZE users;
```

## Auto-fix
This rule is not auto-fixable. Where the `ANALYZE` belongs depends on how the backfill is structured — appending it after the first batch of a loop would be worse than useless. Adding one line at the end of the backfill is the whole fix.
