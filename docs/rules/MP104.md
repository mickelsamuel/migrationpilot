# MP104: warn-long-index-build

**Severity**: Warning | **Auto-fixable**: No | **Tier**: Free (needs `--database-url`)

## What It Detects
An index build on a table large enough that the build runs for a long time. The rule estimates a duration range from the live row count and fires when the slow end of that range crosses five minutes — roughly 37M rows for a plain `CREATE INDEX`, or 12M for `CONCURRENTLY`.

## Why It's Dangerous
Build time scales with row count, and a long build is a long exposure to whatever the build costs you.

A plain `CREATE INDEX` holds a SHARE lock, which blocks every write on the table until it finishes. `CONCURRENTLY` does not block writes, but it makes two passes over the table and holds a snapshot the whole time, which stops vacuum from cleaning up dead rows anywhere in the database — a long build on one table can bloat every other table. And if a `CONCURRENTLY` build fails or is cancelled, it leaves an INVALID index behind that has to be dropped and rebuilt.

## Requires Production Context
MP104 reads the row count from `pg_class.reltuples`. Without `--database-url` it has no idea how large the table is and stays silent.

### About the estimate
The range is wide on purpose, and it is a range rather than a number because build speed genuinely varies by more than an order of magnitude. The fast end (2M rows/sec) is a narrow integer key on a warm, uncontended machine; the slow end (125k rows/sec) matches a wide unique key on cloud storage under load. `CONCURRENTLY` is treated as three times slower, which is the usual figure for two table scans plus the waits between them.

Treat the output as an order of magnitude, not a schedule. What actually decides the number on your system is key width, `maintenance_work_mem`, parallel workers, and I/O — and the rule reports `maintenance_work_mem` and `max_parallel_maintenance_workers` when the server exposes them, because raising both is the cheapest way to move the estimate.

## Bad Example
```sql
-- events has 500M rows
CREATE INDEX idx_events_ts ON events (created_at);
```

## Good Example
```sql
-- Give the build room, then build without blocking writes:
SET maintenance_work_mem = '2GB';
SET max_parallel_maintenance_workers = 4;

CREATE INDEX CONCURRENTLY idx_events_ts ON events (created_at);
```

Watch it while it runs:

```sql
SELECT phase, blocks_done, blocks_total, tuples_done, tuples_total
FROM pg_stat_progress_create_index;
```

And check afterwards that nothing was left behind by a cancelled build:

```sql
SELECT indexrelid::regclass FROM pg_index WHERE NOT indisvalid;
```

## Auto-fix
This rule is not auto-fixable. [MP001](./MP001.md) handles adding `CONCURRENTLY`; the rest is a scheduling decision.
