# MP103: warn-replication-lag-risk

**Severity**: Warning | **Auto-fixable**: No | **Tier**: Free (needs `--database-url`)

## What It Detects
A WAL-heavy operation — a table rewrite, an index build, a REINDEX, a large UPDATE or DELETE, or an `INSERT ... SELECT` — on a table of 1 GB or 5M rows and up, while `pg_stat_replication` shows connected standbys.

## Why It's Dangerous
All of that work goes through WAL, and a standby replays WAL with a single startup process. Work the primary spread across many backends arrives at the replica serially, so lag grows for as long as the operation runs and for some time after it finishes.

Two things follow. If any reads are served from replicas, they serve stale data for that whole window — and the staleness is measured in the size of your migration, not in your usual sub-second lag. And if you fail over while the lag is high, whatever has not been replayed is gone.

Replication slots turn the pressure around. If a replica cannot keep up, the primary keeps WAL for it, and a long enough backlog fills the primary's disk. `max_slot_wal_keep_size` is what stops that, and it is worth confirming before a large operation rather than after.

## Requires Production Context
MP103 needs to know that replicas exist, which comes from `pg_stat_replication`, and how large the table is, which comes from `pg_class`. Without `--database-url` it has neither and stays silent.

When the connected role can read the LSN columns — it needs `pg_monitor` or `pg_read_all_stats` — the message also reports the current replay lag. Without those privileges the replica count still works and the lag is simply left out.

## Bad Example
```sql
-- events is 60 GB, two streaming replicas connected
UPDATE events SET processed = true WHERE processed IS NULL;
```

## Good Example
```sql
-- Batch the work, and let replicas catch up between batches:
DO $$
DECLARE
  rows_updated INT;
BEGIN
  LOOP
    UPDATE events SET processed = true
    WHERE ctid IN (
      SELECT ctid FROM events WHERE processed IS NULL LIMIT 10000
    );
    GET DIAGNOSTICS rows_updated = ROW_COUNT;
    EXIT WHEN rows_updated = 0;
    COMMIT;
    PERFORM pg_sleep(0.5);
  END LOOP;
END $$;
```

Watch the lag while it runs:

```sql
SELECT client_addr,
       state,
       pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), replay_lsn)) AS replay_lag
FROM pg_stat_replication;
```

## Auto-fix
This rule is not auto-fixable. Batching a backfill safely means knowing which rows to process and in what order, which is specific to the migration.
