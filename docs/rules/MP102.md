# MP102: warn-rewrite-disk-headroom

**Severity**: Warning | **Auto-fixable**: No | **Tier**: Free (needs `--database-url`)

## What It Detects
A full-table rewrite on a table of 1 GB or more: `VACUUM FULL`, `CLUSTER`, `ALTER COLUMN ... TYPE`, `SET LOGGED` / `SET UNLOGGED`, or `ADD COLUMN` with a volatile default.

## Why It's Dangerous
None of these edit the table in place. PostgreSQL builds a complete new copy — heap and indexes — and only drops the original once the new copy is committed, so peak usage is roughly twice the current size. On a 400 GB table that is 400 GB of free space you need to have and probably were not thinking about.

Running out of space partway through does not corrupt anything, but it does mean the rewrite fails and rolls back, and you have paid the full ACCESS EXCLUSIVE lock duration for nothing. On a large table that is hours of downtime with no result.

## Requires Production Context
MP102 reads `pg_total_relation_size()` for the target table. Without `--database-url` it does not know the table's size and stays silent.

Free space is a separate matter. Released PostgreSQL has no function that reports it — `pg_tablespace_avail()` has been proposed on pgsql-hackers but is not in any released version as of PG18 — so in almost every case MP102 reports the sizes and tells you to check the volume yourself. If your server defines a `pg_tablespace_avail(name)` function returning bytes (some teams add one with `plperlu`), MigrationPilot feature-detects it and includes real headroom numbers in the message.

`REINDEX` is deliberately out of scope. It also needs room for a second copy, but of the index rather than the table, and MigrationPilot's table stats do not separate index size from total size — so the arithmetic would be wrong. Check index sizes by hand before a large REINDEX.

## Bad Example
```sql
-- orders is 400 GB; the volume has 120 GB free
VACUUM FULL orders;
```

## Good Example
```sql
-- Check the volume first:
--   df -h $(psql -tAc "SHOW data_directory")

-- And what the copy will cost:
SELECT pg_size_pretty(pg_total_relation_size('orders')) AS current_size,
       pg_size_pretty(pg_total_relation_size('orders') * 2) AS peak_during_rewrite;
```

If the goal is to reclaim bloat rather than to rewrite the table, `pg_repack` does it without the ACCESS EXCLUSIVE lock:

```bash
pg_repack --table=orders --no-superuser-check mydb
```

It still needs the same second copy, so the disk requirement does not change — only the locking does.

## Auto-fix
This rule is not auto-fixable. There is no rewriting of the statement that removes the need for the space.
