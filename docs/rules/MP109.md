# MP109: require-vector-index-params

**Severity**: Warning | **Auto-fixable**: No | **Tier**: Free

## What It Detects
A pgvector index created without its build parameters: an HNSW index with no `m` or `ef_construction`, or an IVFFlat index with no `lists`.

## Why It's Dangerous
These are build-time decisions, and they are expensive to revisit.

For HNSW, `m` and `ef_construction` set the shape of the graph and therefore the recall ceiling. The defaults — `m = 16`, `ef_construction = 64` — are conservative, and teams with a recall target frequently need more than that. For IVFFlat, `lists` decides how the vectors are clustered, and pgvector ties the right value to the row count: `rows / 1000` up to a million rows, `sqrt(rows)` beyond that. A default that ignores the row count is a default that is wrong at scale in one direction or the other.

Changing any of them later means rebuilding the whole index, which on a vector table is one of the most expensive builds PostgreSQL will do for you.

## Static Rule
Unlike the rest of the MP100 block, MP109 works from the migration file alone — the absence of a `WITH` clause is visible without a database.

Production context makes it more specific rather than enabling it: when MigrationPilot knows the row count, it computes the IVFFlat starting value for you instead of quoting the formula.

## Bad Example
```sql
CREATE INDEX idx_items_embedding ON items USING hnsw (embedding vector_cosine_ops);

CREATE INDEX idx_docs_embedding ON documents USING ivfflat (embedding vector_l2_ops);
```

## Good Example
```sql
CREATE INDEX idx_items_embedding ON items
  USING hnsw (embedding vector_cosine_ops)
  WITH (m = 16, ef_construction = 128);

-- lists sized to the data: 4M rows -> sqrt(4,000,000) = 2,000
CREATE INDEX idx_docs_embedding ON documents
  USING ivfflat (embedding vector_l2_ops)
  WITH (lists = 2000);
```

Higher `ef_construction` buys recall at the cost of build time; higher `m` raises recall and index size. Measure against a known-good result set before committing, because changing your mind means rebuilding.

The query-time knobs are separate and can be changed freely:

```sql
SET hnsw.ef_search = 100;   -- HNSW
SET ivfflat.probes = 10;    -- IVFFlat
```

## Interaction with MP050
[MP050](./MP050.md) argues for HNSW over IVFFlat. MP109 fires on both, so an IVFFlat index with no `lists` gets two findings: one saying you probably want HNSW, one saying that if you are keeping IVFFlat, size the clustering. That is intentional — MP050 is a preference some teams disable on purpose, and the tuning advice should not disappear with it.

## Auto-fix
This rule is not auto-fixable. There is no correct default to insert: the right values depend on your recall target, your vector dimensions, and how large the table will get.
