# MP098: warn-set-schema

**Severity**: Warning | **Auto-fixable**: No | **Tier**: Free

## What It Detects
`ALTER ... SET SCHEMA` on any object that supports it — tables, views, materialized views, sequences, functions, types, domains, foreign tables.

## Why It's Dangerous
Moving an object between schemas is a rename in every way that matters, and it takes effect all at once. Every query that named the object as `old_schema.thing` starts failing the instant the migration commits:

```
ERROR: relation "public.users" does not exist
```

There is no deprecation window. The old path stops working at exactly the moment the new one starts, so the application has to be updated in the same instant — which is not something a deploy can actually guarantee, since old and new application versions overlap during a rolling restart.

Unqualified references are the more insidious half. They resolve through `search_path`, which is per-role and per-session, so whether they still work depends on who is asking. The migration succeeds. Your `psql` session, which probably has a broad `search_path`, looks fine. The application role, which may have a narrower one, is broken. Testing the migration by hand can therefore tell you nothing useful.

Views and functions that reference the object follow it automatically — PostgreSQL tracks those dependencies. The SQL embedded in your application does not.

## Bad Example
```sql
ALTER TABLE users SET SCHEMA archive;
-- Every "public.users" reference breaks at commit
```

## Good Example
```sql
-- Move it, then leave a view behind at the old path
ALTER TABLE public.users SET SCHEMA archive;
CREATE VIEW public.users AS SELECT * FROM archive.users;
```

Ship the application change, confirm nothing reads the old path, then remove the shim in a later migration:

```sql
DROP VIEW public.users;
```

Note that a simple view over a single table is updatable, so writes continue to work through the shim. Check what still depends on the old path before cutting over:

```sql
SELECT DISTINCT dependent_ns.nspname, dependent_view.relname
FROM pg_depend
JOIN pg_rewrite ON pg_depend.objid = pg_rewrite.oid
JOIN pg_class AS dependent_view ON pg_rewrite.ev_class = dependent_view.oid
JOIN pg_namespace AS dependent_ns ON dependent_view.relnamespace = dependent_ns.oid
WHERE pg_depend.refobjid = 'archive.users'::regclass;
```

## Auto-fix
This rule is not auto-fixable. Whether a compatibility view is appropriate — and whether it needs to be updatable — depends on how the object is used, and the cutover has to be sequenced against an application deploy.
