# MP100: warn-redundant-index

**Severity**: Warning | **Auto-fixable**: No | **Tier**: Free (needs `--database-url`)

## What It Detects
A `CREATE INDEX` whose key columns are already the leading columns of an index that exists on the table in production.

## Why It's Dangerous
PostgreSQL can use the leading columns of a composite index on their own, so an index on `(tenant_id)` adds no lookup path that an existing index on `(tenant_id, created_at)` did not already provide. What it does add is a full build, permanent disk, and work on every INSERT, UPDATE, and DELETE for as long as the index exists. Redundant indexes also make planning marginally slower, because the planner considers each one.

The migration file cannot tell you this on its own — it needs the catalog of what is already there. That is why MP100 only fires with `--database-url`.

## Requires Production Context
MP100 compares against `pg_index` for the target table. Without `--database-url` there is nothing to compare against and the rule stays silent, the same way MP013 does.

To keep false positives out, it stays quiet in every case where the two indexes are not interchangeable:

- different access method (a GIN index does not cover a B-tree one)
- either index is partial
- the new index uses an expression rather than plain columns
- the new index is `UNIQUE` and the existing one is not, or is unique on a different number of columns — uniqueness on `(a)` is a stronger constraint than uniqueness on `(a, b)`

## Bad Example
```sql
-- Production already has:
--   CREATE INDEX idx_users_tenant_created ON users (tenant_id, created_at);

CREATE INDEX CONCURRENTLY idx_users_tenant ON users (tenant_id);
```

## Good Example
```sql
-- Nothing to add: idx_users_tenant_created already serves lookups on tenant_id.
-- Confirm with the planner before deciding you need another index:
EXPLAIN (BUFFERS) SELECT * FROM users WHERE tenant_id = $1;
```

If the narrower index really is worth having — a much smaller index for a very hot lookup, a different sort order, or a different access method — keep it and disable the rule for that statement:

```sql
-- migrationpilot-disable MP100
CREATE INDEX CONCURRENTLY idx_users_tenant ON users (tenant_id);
```

## Auto-fix
This rule is not auto-fixable. Whether an index is genuinely redundant depends on the queries you run, and only you can answer that. Check what the existing index costs and what it serves:

```sql
SELECT indexrelname,
       idx_scan,
       pg_size_pretty(pg_relation_size(indexrelid)) AS size
FROM pg_stat_user_indexes
WHERE relname = 'users'
ORDER BY idx_scan;
```

## Configuration
```yaml
rules:
  MP100: false           # disable
  MP100:
    severity: critical   # change severity
```
