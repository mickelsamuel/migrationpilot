# MP087: ban-volatile-check-constraint

**Severity**: Critical | **Auto-fixable**: No | **Tier**: Free

## What It Detects
A `CHECK` constraint whose expression calls a volatile function — `now()`, `random()`, `clock_timestamp()`, `gen_random_uuid()`, `nextval()` and friends, including bare `CURRENT_TIMESTAMP` and calls nested inside subqueries. Detection walks the parsed expression, so a column named `random_seed` or `now_utc` does not trip it.

## Why It's Dangerous
PostgreSQL does not require `CHECK` expressions to be `IMMUTABLE`. It accepts this constraint without a warning, and that is exactly the problem — there is no error to catch in review.

A `CHECK` is evaluated when a row is written and never again. Build one on `now()` and it stops describing the rows it admitted:

```sql
CREATE TABLE sessions (id int, expires_at timestamptz CHECK (expires_at > now()));
INSERT INTO sessions VALUES (1, now() + interval '2 seconds');  -- accepted
-- ...two seconds pass...
```

The row is still there and still readable. The table now contains data that violates its own constraint, and `\d sessions` still lists the constraint as though it means something.

Two consequences follow, both delayed:

**The row becomes un-updatable.** Any `UPDATE` re-checks the constraint against the new row version, so writing to a completely unrelated column fails:

```sql
UPDATE sessions SET id = id;
ERROR: new row for relation "sessions" violates check constraint "sessions_expires_at_check"
```

**The backup will not restore.** Restoring a dump re-adds the constraint against the stored data, which fails:

```
ERROR: check constraint "sessions_expires_at_check" of relation "sessions" is violated by some row
```

You discover that during a restore, which is the worst available moment. Note that an in-place table rewrite — `ALTER TABLE ... ALTER COLUMN ... TYPE` — does *not* re-check the constraint, so a rewrite succeeding tells you nothing about whether a restore would.

## Bad Example
```sql
ALTER TABLE sessions ADD CONSTRAINT sessions_not_expired
  CHECK (expires_at > now());
-- Accepted. Rots silently. Blocks UPDATEs and restores later.
```

## Good Example
```sql
-- Compare stored values against each other — an invariant that stays true.
ALTER TABLE sessions ADD CONSTRAINT sessions_expiry_after_creation
  CHECK (expires_at > created_at) NOT VALID;
ALTER TABLE sessions VALIDATE CONSTRAINT sessions_expiry_after_creation;
```

If the rule really is relative to the current time, enforce it somewhere it can be re-evaluated — a `WHERE expires_at > now()` in the query, a partial index, or a trigger — rather than a constraint frozen at insert time.

## Auto-fix
This rule is not auto-fixable. Replacing a time-relative predicate with one over stored columns means deciding what the invariant actually is, and there is no mechanical translation from one to the other.
