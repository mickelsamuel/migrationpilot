# MP085: warn-grant-widening

**Severity**: Warning | **Auto-fixable**: No | **Tier**: Free

## What It Detects
`GRANT` statements that hand out more than a specific privilege to a specific role:

- `GRANT ... TO PUBLIC` — any privilege granted to the `PUBLIC` pseudo-role
- `GRANT ALL` — no explicit privilege list, so the whole set
- `GRANT ... ON ALL TABLES IN SCHEMA ...` — a blanket grant across the schema

`REVOKE` is not flagged; it narrows access rather than widening it.

## Why It's Dangerous
Privileges granted in a migration are permanent and almost never revisited. Nobody opens a two-year-old migration to check what it granted, so whatever it did is now simply how the database is.

`TO PUBLIC` is the one that resists auditing. It does not grant to the roles that exist — it grants to the role every user implicitly has, including users created long after the migration ran. Listing your current roles and their grants will not show you who can reach the table, because the answer is everyone.

`GRANT ALL` is usually shorthand for "the app needs to read and write this". It also confers `TRUNCATE`, which can empty the table in one statement, and `REFERENCES`, which lets the grantee create foreign keys that constrain your ability to delete rows later.

A schema-wide grant applies to the tables that happen to exist when it runs. Add a table in a later migration and it is not covered; re-run the grant and it is. The resulting privilege set depends on migration ordering rather than on anything anyone decided.

## Bad Example
```sql
GRANT ALL ON users TO app;
-- app can now TRUNCATE users

GRANT SELECT ON users TO PUBLIC;
-- every role in the cluster, including ones created next year

GRANT SELECT ON ALL TABLES IN SCHEMA public TO reporting;
-- covers today's tables; tomorrow's are a coin flip
```

## Good Example
```sql
-- Name the privileges, name the role.
GRANT SELECT, INSERT, UPDATE ON users TO app_role;

-- For future tables, set the default explicitly rather than
-- re-running a blanket grant.
ALTER DEFAULT PRIVILEGES IN SCHEMA public
  GRANT SELECT ON TABLES TO reporting;

-- If PUBLIC access was inherited from an older migration, remove it.
REVOKE ALL ON users FROM PUBLIC;
```

## Auto-fix
This rule is not auto-fixable. Narrowing a grant means knowing which privileges the application actually uses, and guessing wrong locks out working code. Check what the role does before trimming — `pg_stat_statements` filtered by that role is a reasonable starting point.
