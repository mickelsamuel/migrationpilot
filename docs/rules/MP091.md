# MP091: warn-privilege-drift

**Severity**: Warning | **Auto-fixable**: No | **Tier**: Free

## What It Detects
`GRANT` or `REVOKE` — on objects or on role membership — in a migration file that also contains DDL. A migration containing only privilege statements is not flagged, and neither is one containing only DDL. Reported once per file rather than once per statement.

## Why It's Dangerous
A `GRANT` in the middle of a schema migration is a permanent access-control change being reviewed as though it were a schema change. The reviewer is checking whether the column type is right; the privilege line goes past in the same diff.

The auditing problem is the durable one. "Who can read this table, and who approved that?" has no answer short of replaying every migration in order, because the migration history *is* the record — there is no single file describing the access model. Ownership makes this worse: the schema is owned by whoever owns the schema, but access decisions usually belong to someone else, and merging them into one file merges the two review processes into whichever one is weaker.

Rollback is asymmetric too. Reverting the schema change does not revert the grant. DDL rollbacks restore structure; the privileges that rode along stay exactly where they are, so a rolled-back migration can leave behind access nobody intended to keep.

This is the same separation [MP080](./MP080.md) asks for between schema and data, applied to access control.

## Bad Example
```sql
-- migrations/012_add_reports.sql
CREATE TABLE reports (id BIGINT PRIMARY KEY, body TEXT);
CREATE INDEX idx_reports_created ON reports (created_at);
GRANT SELECT ON reports TO analyst;
-- Access decision buried in a schema diff
```

## Good Example
```sql
-- migrations/012_add_reports.sql  — schema only
CREATE TABLE reports (id BIGINT PRIMARY KEY, body TEXT);
CREATE INDEX idx_reports_created ON reports (created_at);
```

```sql
-- migrations/013_grant_reports_access.sql  — privileges only
GRANT SELECT ON reports TO analyst;
```

Two files, two reviews, and a search for `GRANT` across the migrations directory returns something meaningful.

## Auto-fix
This rule is not auto-fixable. Splitting a migration changes how it is applied and ordered, which is a decision for whoever owns the deployment process.
