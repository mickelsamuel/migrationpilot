# MP092: require-partitioned-index-strategy

**Severity**: Warning | **Auto-fixable**: No | **Tier**: Free

## What It Detects
`CREATE INDEX` targeting a partitioned parent table, in two shapes:

- with `CONCURRENTLY`, which PostgreSQL rejects outright
- without `ONLY`, which recursively builds an index on every partition

Whether a table is a partitioned parent is determined from the migration itself — a `CREATE TABLE ... PARTITION BY`, a `CREATE TABLE ... PARTITION OF it`, or an `ATTACH PARTITION` onto it. `CREATE INDEX ON ONLY parent` is the recommended first step and is not flagged.

## Why It's Dangerous
Indexing a partitioned parent does not behave like indexing a table, and the habit that keeps index builds safe everywhere else fails here:

```
ERROR: cannot create index on partitioned table "events" concurrently
```

`CONCURRENTLY` is simply not available on a partitioned parent. If your team's rule is "always use CONCURRENTLY" — which [MP001](./MP001.md) exists to enforce — then the first time someone applies it to a partitioned table the migration fails at run time, after it has started.

Drop the `CONCURRENTLY` and it is accepted, which is the trap. One statement now builds an index on every partition, holding locks across the whole hierarchy until the last one completes. On a table partitioned by month over three years that is thirty-six index builds in a single lock window, and there is no way to stop partway or observe progress.

The supported approach separates the two things. `CREATE INDEX ON ONLY parent` creates a catalog entry with no storage — it is marked invalid and takes almost no time. Each partition then gets its own index built `CONCURRENTLY`, one at a time, each of which is online and interruptible. Attaching the last partition index flips the parent index to valid.

## Bad Example
```sql
CREATE TABLE events (id BIGINT, ts TIMESTAMPTZ) PARTITION BY RANGE (ts);

CREATE INDEX CONCURRENTLY idx_events_id ON events (id);
-- ERROR: cannot create index on partitioned table "events" concurrently

CREATE INDEX idx_events_id ON events (id);
-- Accepted, but builds on every partition under lock
```

## Good Example
```sql
-- Catalog-only parent index: instant, marked invalid until filled in
CREATE INDEX idx_events_id ON ONLY events (id);

-- One partition at a time, each build online
CREATE INDEX CONCURRENTLY idx_events_id_2026_01 ON events_2026_01 (id);
ALTER INDEX idx_events_id ATTACH PARTITION idx_events_id_2026_01;

CREATE INDEX CONCURRENTLY idx_events_id_2026_02 ON events_2026_02 (id);
ALTER INDEX idx_events_id ATTACH PARTITION idx_events_id_2026_02;
-- ...parent index becomes valid once every partition is attached
```

Check that it made it:

```sql
SELECT indexrelid::regclass, indisvalid FROM pg_index
WHERE indrelid = 'events'::regclass;
```

## Auto-fix
This rule is not auto-fixable. The safe form needs one statement pair per partition, and the partition names are not derivable from the `CREATE INDEX` statement.
