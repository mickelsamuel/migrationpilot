# MP108: warn-partman-managed-parent

**Severity**: Warning | **Auto-fixable**: No | **Tier**: Free (needs `--database-url`)

## What It Detects
Hand-written partition DDL — `CREATE TABLE ... PARTITION OF`, `ATTACH PARTITION`, or `DETACH PARTITION` — against a parent table that appears in pg_partman's `part_config`.

## Why It's Dangerous
pg_partman decides which children exist, from what `part_config` says. `run_maintenance` pre-creates the next few partitions according to `premake` and drops old ones according to `retention`, on its own schedule.

A partition created, attached, or detached by hand is not recorded there. The next maintenance run can try to create a partition whose range you have already covered — which fails — or drop one it believes it owns. Worse, the two systems disagree quietly: nothing goes wrong at migration time, and the failure surfaces later on a scheduled maintenance run that nobody is watching.

## Requires Production Context
`part_config` is the only place that says a parent is managed, and MigrationPilot reads it from whichever schema pg_partman is installed into. Without `--database-url` the rule stays silent, and a `CREATE TABLE ... PARTITION OF` looks like ordinary partition DDL.

The message includes the control column, interval, premake, and retention when they are readable, because those are what tell you whether your manual partition sits inside or outside what partman is about to do.

## Bad Example
```sql
-- events is managed by pg_partman (interval 1 day, premake 4, retention 90 days)
CREATE TABLE events_p2024_01 PARTITION OF events
  FOR VALUES FROM ('2024-01-01') TO ('2024-02-01');
```

## Good Example
```sql
-- Check what partman thinks it owns:
SELECT parent_table, control, partition_interval, premake, retention, automatic_maintenance
FROM part_config WHERE parent_table LIKE '%events';

-- Let partman make the partitions, by widening how far ahead it pre-creates:
UPDATE part_config SET premake = 8 WHERE parent_table = 'public.events';
CALL run_maintenance_proc();
```

To move existing rows into the partition set, use partman's own procedure — it commits in batches instead of one long transaction:

```sql
CALL partition_data_proc('public.events');
```

If the partition set genuinely should be managed by hand from now on, take it out of partman first rather than working around it:

```sql
DELETE FROM part_config WHERE parent_table = 'public.events';
```

## Auto-fix
This rule is not auto-fixable. Whether the right answer is to reconfigure partman or to hand the table back to you is a decision about how the partition set is meant to be run.
