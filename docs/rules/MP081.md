# MP081: prefer-pg18-not-null-not-valid

**Severity**: Warning | **Auto-fixable**: No | **Tier**: Free

## What It Detects
The old `CHECK (col IS NOT NULL) NOT VALID` workaround on PostgreSQL 18 and above, where native syntax makes it unnecessary. Only fires when the target version is PG18+.

## Why It's Dangerous
PostgreSQL 18 stores NOT NULL constraints in `pg_constraint`, so `ALTER TABLE ... ADD CONSTRAINT ... NOT NULL col NOT VALID` marks a column NOT NULL without scanning the table — the operation is instant. Before PG18, the only safe way to add a NOT NULL constraint to a populated table was a four-step dance: add a `CHECK (col IS NOT NULL) NOT VALID` constraint, validate it, run `SET NOT NULL` (which PostgreSQL can then prove instantly), and finally drop the now-redundant CHECK. That workaround still works on PG18, but it is four statements where two will do, and each extra step is a place to make a mistake or to leave a stray constraint behind. This rule does not overlap with MP002, which catches a bare `SET NOT NULL`; MP081 catches the workaround that PG18 made obsolete.

## Bad Example
```sql
-- PG18+: the old workaround, no longer needed
ALTER TABLE users ADD CONSTRAINT users_email_nn
  CHECK (email IS NOT NULL) NOT VALID;
ALTER TABLE users VALIDATE CONSTRAINT users_email_nn;
-- Two more statements still to come: SET NOT NULL, then DROP CONSTRAINT
-- Leaves a redundant CHECK behind if you forget the cleanup
```

## Good Example
```sql
-- PG18+ native approach (simpler, same safety)
ALTER TABLE users ADD CONSTRAINT users_email_not_null
  NOT NULL email NOT VALID;
ALTER TABLE users VALIDATE CONSTRAINT users_email_not_null;
```

## Auto-fix
This rule is not auto-fixable. Rewriting the workaround means collapsing several statements into two and dropping the temporary constraint, which depends on how your migration is structured. Replace the CHECK-based sequence with a named `NOT NULL ... NOT VALID` constraint followed by `VALIDATE CONSTRAINT`.

