# MP089: warn-collation-change-rewrite

**Severity**: Warning | **Auto-fixable**: No | **Tier**: Free

## What It Detects
`ALTER TABLE ... ALTER COLUMN ... TYPE ... COLLATE ...` — a column type change that carries a `COLLATE` clause. Both the `TYPE` and `SET DATA TYPE` spellings are covered.

## Why It's Dangerous
A collation is the definition of sort order, so changing it changes where every value in the column belongs. That has two costs, one immediate and one permanent.

The immediate one is the rebuild. Every btree index on the column is ordered by the old collation and is now wrong, so PostgreSQL rebuilds it — inside the same `ACCESS EXCLUSIVE` lock as the table rewrite, not as separate work you can schedule or run concurrently. A column with three indexes on a large table means the table is unavailable until the last of them finishes.

The permanent one is that comparisons answer differently afterwards. `ORDER BY` returns a different sequence, range predicates match a different set of rows, and `LIKE 'foo%'` may stop using an index that was valid under the old collation. If the column has a unique index, a collation that treats more strings as equal can start rejecting inserts that used to succeed — and one that treats fewer as equal can let through duplicates the old collation prevented. None of this shows up in the migration; it shows up in queries afterwards.

Note that [MP007](./MP007.md) also fires on this statement, for the rewrite that any `ALTER COLUMN TYPE` causes. This rule covers what is specific to collation.

## Bad Example
```sql
ALTER TABLE users ALTER COLUMN name TYPE TEXT COLLATE "en_US";
-- Table rewritten, every index on name rebuilt, all under ACCESS EXCLUSIVE
```

## Good Example
```sql
-- Expand-contract keeps the index builds online.
ALTER TABLE users ADD COLUMN name_new TEXT COLLATE "en_US";
-- backfill in batches...
CREATE INDEX CONCURRENTLY idx_users_name_new ON users (name_new);
-- swap the columns in a short transaction once the data is in place
```

If it has to happen in place, bound the lock wait so the statement fails fast rather than queueing at the head of the lock queue:

```sql
SET lock_timeout = '5s';
ALTER TABLE users ALTER COLUMN name TYPE TEXT COLLATE "en_US";
RESET lock_timeout;
```

## Auto-fix
This rule is not auto-fixable. Whether the new sort order is correct for your data is the entire question, and rewriting the statement mechanically would not answer it. Before changing a collation in place, check what depends on the column:

```sql
SELECT indexname, indexdef FROM pg_indexes
WHERE tablename = 'users' AND indexdef LIKE '%name%';
```
