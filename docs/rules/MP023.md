# MP023: require-if-not-exists

**Severity**: Warning | **Auto-fixable**: No | **Tier**: Free

## What It Detects
CREATE TABLE/INDEX without IF NOT EXISTS will fail if the object already exists, making migrations non-idempotent.

## Why It's Dangerous
Without IF NOT EXISTS, re-running a migration fails with "relation already exists". Idempotent migrations are safer for retry and rollback scenarios, and required by many deployment pipelines.

## The Exception: Concurrent Index Builds
This rule says nothing about `CREATE INDEX CONCURRENTLY`, in either direction. There, `IF NOT
EXISTS` is not idempotency — it is a way to lose an index silently. A concurrent build that fails
leaves an index behind marked invalid, and it still holds the name; `IF NOT EXISTS` matches the
name, skips the rebuild, and returns the `CREATE INDEX` success tag. The migration is recorded as
applied over an index that will never answer a query, with nothing in the deploy log.

The retry-safe form is a preceding `DROP INDEX CONCURRENTLY IF EXISTS`, which is
[MP070](./MP070.md)'s subject and handbook
[MPH-012](../handbook/12-invalid-index-after-failed-concurrently.md)'s. `--fix` will not add
`IF NOT EXISTS` to a concurrent build for the same reason.

## Bad Example
```sql
CREATE TABLE users (
  id bigint PRIMARY KEY,
  email text
);

CREATE INDEX idx_users_email ON users (email);
```

## Good Example
```sql
CREATE TABLE IF NOT EXISTS users (
  id bigint PRIMARY KEY,
  email text
);

CREATE INDEX IF NOT EXISTS idx_users_email ON users (email);
```

For an index on a table that already has traffic, the safe build is the concurrent one, and it
does not take `IF NOT EXISTS` at all — see [MP001](./MP001.md).

## Auto-fix
`migrationpilot analyze <file> --fix` fixes this. Insert IF NOT EXISTS into CREATE TABLE/INDEX, making the statement idempotent.

See [auto-fix](../auto-fix.md).
