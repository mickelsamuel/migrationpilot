# MP001: require-concurrent-index-creation

**Severity**: Critical | **Auto-fixable**: Yes | **Tier**: Free

## What It Detects
CREATE INDEX without CONCURRENTLY blocks all writes on the target table for the entire duration of index creation.

## Why It's Dangerous
Without CONCURRENTLY, PostgreSQL holds a SHARE lock on the table for the entire index build.
Reads keep working; every INSERT, UPDATE and DELETE blocks until the build finishes. On a table
with millions of rows that is minutes of writes queued behind one statement, and every connection
waiting on them.

(SHARE, not ACCESS EXCLUSIVE — the lock table in the same report says so. ACCESS EXCLUSIVE is what
a non-concurrent `DROP INDEX` takes; see [MP009](./MP009.md).)

## Bad Example
```sql
CREATE INDEX idx_users_email ON users (email);
```

## Good Example
```sql
SET lock_timeout = '5s';
-- Clear an invalid index left by an earlier failed attempt. Do not use
-- IF NOT EXISTS here: it would skip the build and report success over it.
DROP INDEX CONCURRENTLY IF EXISTS idx_users_email;
CREATE INDEX CONCURRENTLY idx_users_email ON users (email);
```

Adding `CONCURRENTLY` on its own trades one problem for another: a concurrent build that fails
leaves an INVALID index behind, and the retry has to clear it first — that is
[MP070](./MP070.md), and handbook [MPH-012](../handbook/12-invalid-index-after-failed-concurrently.md)
is the long version. Note what is *not* in the recipe: no `statement_timeout`, because a timeout
firing partway through a concurrent build is one of the ways the index ends up invalid; and no
`IF NOT EXISTS`, because it matches the invalid index by name and skips the rebuild.

If a `UNIQUE` or `PRIMARY KEY` constraint owns the index, PostgreSQL refuses the drop outright.
Rebuild in place instead: `REINDEX INDEX CONCURRENTLY idx_users_email;`.

`migrationpilot analyze <file> --fix` fixes this. Insert CONCURRENTLY into CREATE [UNIQUE] INDEX — same index, non-blocking build.
