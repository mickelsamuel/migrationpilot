# MP105: warn-timescale-hypertable-ddl

**Severity**: Warning | **Auto-fixable**: No | **Tier**: Free (needs `--database-url`)

## What It Detects
`ALTER TABLE`, `RENAME`, or `CREATE INDEX` against a table that TimescaleDB's catalog says is a hypertable.

## Why It's Dangerous
A hypertable is a facade. The data lives in chunks, each a real table, and TimescaleDB applies schema changes to the hypertable and to every one of them. So a statement that reads like one table's worth of work takes locks across the whole set and runs until the slowest chunk is done. On a hypertable with hundreds of chunks that is a very different operation from what the migration file suggests.

Index creation has a specific catch: TimescaleDB does not support `CREATE INDEX CONCURRENTLY` on a hypertable. If your migration has it, the statement fails rather than running slowly. The documented alternative is `WITH (timescaledb.transaction_per_chunk)`, which builds chunk by chunk in separate transactions so only one chunk is blocked at a time.

## Requires Production Context
Hypertable membership lives in TimescaleDB's own catalog — `timescaledb_information.hypertables`, with `_timescaledb_catalog.hypertable` as a fallback on versions where the view's columns differ. Nothing in the migration file says a table is a hypertable, and a `create_hypertable()` call in a different file is out of scope by design. Without `--database-url` the rule stays silent.

The chunk count and the compression flag come from the same view, which is why the message can tell you how many chunks the statement will actually touch.

## Bad Example
```sql
-- metrics is a hypertable with 420 chunks
CREATE INDEX CONCURRENTLY idx_metrics_device ON metrics (device_id);
-- ERROR: CREATE INDEX CONCURRENTLY is not supported on hypertables
```

## Good Example
```sql
CREATE INDEX idx_metrics_device ON metrics (device_id)
  WITH (timescaledb.transaction_per_chunk);
```

Two caveats on `transaction_per_chunk`: it does not work for `CREATE UNIQUE INDEX`, and if it fails partway through, some chunks keep the index while the hypertable's index is marked invalid. A unique index on a hypertable must also include all of the partitioning columns.

For an `ALTER TABLE`, check the fan-out first and fail fast rather than queueing:

```sql
SELECT hypertable_name, num_chunks, compression_enabled
FROM timescaledb_information.hypertables
WHERE hypertable_name = 'metrics';

SET lock_timeout = '5s';
ALTER TABLE metrics ADD COLUMN device_id integer;
RESET lock_timeout;
```

## Auto-fix
This rule is not auto-fixable. Rewriting a `CONCURRENTLY` build as `transaction_per_chunk` changes the failure semantics, which is not a substitution to make on someone's behalf.
