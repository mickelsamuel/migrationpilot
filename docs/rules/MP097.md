# MP097: ban-drop-constraint-backing-index

**Severity**: Critical | **Auto-fixable**: No | **Tier**: Free

## What It Detects
Two shapes:

- `DROP INDEX` naming an index that a `PRIMARY KEY` or `UNIQUE` constraint owns
- `ALTER TABLE ... DROP CONSTRAINT` on a `UNIQUE` constraint

Dropping a primary key constraint is left to [MP055](./MP055.md), which reports the replication consequences specific to that case.

### How ownership is established
This rule claims the statement will fail at runtime, so it only fires when something says the
constraint is really there:

- **The catalog**, when a database connection is available: `pg_constraint.conindid` pointing
  at the index. This is the authority.
- **The migration itself**, otherwise: an `ADD CONSTRAINT ... USING INDEX <name>` that adopts
  the index, or an `ADD CONSTRAINT <name> UNIQUE (...)` that creates one under that name.

The finding says which of the two it used, so the claim can be checked.

The index's *name* is never the answer. `_pkey`, `_key`, `_unique` and `_uniq` are what
PostgreSQL generates for constraint-owned indexes, but nothing stops a plain
`CREATE UNIQUE INDEX projects_slug_key ON projects (slug)` from carrying the same suffix — and
that index drops without complaint, because no constraint owns it. Unique and
constraint-backed are different properties; only `pg_constraint` separates them. Verified on
PostgreSQL 18.3: a plain `CREATE UNIQUE INDEX` has no `conindid` row and `DROP INDEX`
succeeds; after `ADD CONSTRAINT ... UNIQUE USING INDEX` it has one and all of `DROP INDEX`,
`DROP INDEX IF EXISTS` and `DROP INDEX CONCURRENTLY IF EXISTS` fail.

## Why It's Dangerous
A `PRIMARY KEY` or `UNIQUE` constraint owns the index that enforces it, and PostgreSQL will not let the index be dropped on its own:

```
ERROR: cannot drop index users_pkey because constraint users_pkey on table users requires it
```

The statement fails and the migration aborts. That is the good outcome — it is loud and it happens before anything changes.

The bad outcome is the obvious next move. Adding `CASCADE` does make the error go away — by dropping the constraint as well. So a statement written to remove a redundant index instead removes a uniqueness guarantee, and takes every foreign key referencing those columns with it. Nothing errors. The migration succeeds. The application starts writing duplicate rows some time later, and re-adding the constraint afterwards requires a full table scan that fails outright if any duplicates arrived in the meantime.

This usually comes from index-cleanup work — a query that lists unused or duplicate indexes will happily include constraint-backing ones, because at the index level they do look redundant.

## Bad Example
```sql
-- With users_pkey owned by the primary key on users:
DROP INDEX users_pkey;
-- ERROR: cannot drop index users_pkey because constraint ... requires it

DROP INDEX users_email_key CASCADE;
-- Succeeds. Silently drops the UNIQUE constraint and any FK depending on it.
```

Nothing is reported for a `DROP INDEX` on an index no constraint owns, whatever it is
called:

```sql
DROP INDEX CONCURRENTLY IF EXISTS projects_slug_key;
CREATE UNIQUE INDEX CONCURRENTLY projects_slug_key ON projects (slug);
-- A plain unique index. The drop succeeds; this is the retry-safe form MP070 asks for.
```

## Good Example
```sql
-- If you want to keep the guarantee: leave the index alone. It is not redundant.

-- If a failed concurrent build left it invalid, rebuild it in place. DROP INDEX
-- is refused here; REINDEX is not. See MP070.
REINDEX INDEX CONCURRENTLY users_email_key;

-- If you want to remove the guarantee, say so directly:
ALTER TABLE users DROP CONSTRAINT users_email_key;

-- If you want to rebuild the index without losing the guarantee, swap it:
CREATE UNIQUE INDEX CONCURRENTLY users_email_key_new ON users (email);
ALTER TABLE users
  DROP CONSTRAINT users_email_key,
  ADD CONSTRAINT users_email_key UNIQUE USING INDEX users_email_key_new;
```

Before dropping a unique constraint you expect to re-add later, confirm you can:

```sql
SELECT email, count(*) FROM users GROUP BY email HAVING count(*) > 1;
```

## Auto-fix
This rule is not auto-fixable. "Drop the index" and "drop the constraint" are different intentions with different consequences, and the statement does not say which one was meant.
