# MP086: require-explicit-on-delete

**Severity**: Warning | **Auto-fixable**: No | **Tier**: Free

## What It Detects
A foreign key created without an `ON DELETE` clause, in either `ALTER TABLE ... ADD CONSTRAINT` or `CREATE TABLE` (column-level `REFERENCES` and table-level `FOREIGN KEY` alike). An explicit `ON DELETE NO ACTION` is not flagged — the default was chosen rather than inherited.

## Why It's Dangerous
Leave the clause off and you get `NO ACTION`, which refuses to delete a parent row while any child row references it:

```
ERROR: update or delete on table "users" violates foreign key constraint
       "orders_user_id_fkey" on table "orders"
```

That is frequently the behaviour you want. The problem is that nobody decided it. The constraint looks correct in review and behaves perfectly until the first time something tries to delete a referenced row, which may be months later and in a code path nobody connected to this migration — a GDPR deletion job, an admin screen, a cleanup script.

The reverse case is worse. `ON DELETE CASCADE` deletes rows in tables the migration never mentions, and a reviewer who has to infer the deletion behaviour from its absence is not reviewing it. Writing the clause out makes the blast radius of a parent delete visible at the point where it is decided.

## Bad Example
```sql
ALTER TABLE orders ADD CONSTRAINT fk_user
  FOREIGN KEY (user_id) REFERENCES users(id);
-- NO ACTION by default; deleting a user now fails once they have an order
```

## Good Example
```sql
-- Say what should happen. Any of these is fine; the point is choosing.
ALTER TABLE orders ADD CONSTRAINT fk_user
  FOREIGN KEY (user_id) REFERENCES users(id)
  ON DELETE RESTRICT
  NOT VALID;
ALTER TABLE orders VALIDATE CONSTRAINT fk_user;
```

The options:

| Clause | Effect on the child rows |
| --- | --- |
| `NO ACTION` (default) | Parent delete fails; check deferred to end of statement |
| `RESTRICT` | Parent delete fails immediately, never deferred |
| `CASCADE` | Child rows are deleted too |
| `SET NULL` | Child FK column is set to NULL |
| `SET DEFAULT` | Child FK column reverts to its default |

## Auto-fix
This rule is not auto-fixable. The right behaviour depends on what the relationship means — whether an order without a user is a data error or an orphan worth keeping — and that is not visible in the SQL.
