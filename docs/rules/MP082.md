# MP082: warn-not-enforced-constraint

**Severity**: Warning | **Auto-fixable**: No | **Tier**: Free

## What It Detects
Constraints declared `NOT ENFORCED` on PostgreSQL 18 and above. Only fires when the target version is PG18+.

## Why It's Dangerous
PostgreSQL 18 `NOT ENFORCED` constraints exist only as metadata. The database records the constraint and the planner may use it, but it will never reject a row that violates it. That is a legitimate tool — it is useful for documenting an invariant your application already guarantees, or for staging a constraint during a gradual migration — but it reads exactly like a normal constraint in a migration file. If you add a foreign key `NOT ENFORCED` believing it protects referential integrity, nothing will stop invalid data from landing, and nothing will tell you it happened. Worse, a planner that trusts an unenforced constraint can produce wrong results from data that violates it. Declare it deliberately or not at all.

## Bad Example
```sql
ALTER TABLE orders ADD CONSTRAINT fk_user
  FOREIGN KEY (user_id) REFERENCES users(id) NOT ENFORCED;
-- Invalid user_id values will NOT be rejected
-- Reads like a foreign key, protects nothing
```

## Good Example
```sql
-- If you need the constraint enforced, add it safely instead:
ALTER TABLE orders ADD CONSTRAINT fk_user
  FOREIGN KEY (user_id) REFERENCES users(id) NOT VALID;
ALTER TABLE orders VALIDATE CONSTRAINT fk_user;

-- If NOT ENFORCED is genuinely what you want, say why:
-- NOTE: NOT ENFORCED — planner hint only, integrity guaranteed by the
-- order service. Do not assume the database rejects bad user_id here.
```

## Auto-fix
This rule is not auto-fixable. Whether the constraint should be enforced is a decision about your data, not a mechanical rewrite. Either drop `NOT ENFORCED` and validate the constraint, or leave a comment recording why it is intentional.
