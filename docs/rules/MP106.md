# MP106: prefer-timescale-drop-chunks

**Severity**: Warning | **Auto-fixable**: No | **Tier**: Free (needs `--database-url`)

## What It Detects
A `DELETE` on a hypertable whose `WHERE` clause compares the hypertable's time dimension against a bound — the shape of a retention delete.

## Why It's Dangerous
Deleting old data row by row is the most expensive way to do the job: a WAL record per row, a dead tuple per row for vacuum to clean up later, and bloat that stays until the vacuum finishes. On a hypertable that work is also unnecessary. Chunks are already partitioned on the time column, so the rows in a retention window are whole chunks, and `drop_chunks()` drops them as tables. No per-row work, no WAL per row, and the space comes back immediately rather than after a vacuum.

## Requires Production Context
Two things come from TimescaleDB's catalog: that the table is a hypertable at all, and which column is its time dimension (`primary_dimension` in `timescaledb_information.hypertables`). The rule needs the second one — a DELETE filtered on `device_id` is not a retention delete, and without knowing the dimension MigrationPilot cannot tell the two apart. If the server does not report a time dimension, the rule stays silent rather than guessing. Without `--database-url` it stays silent too.

## Bad Example
```sql
DELETE FROM metrics WHERE time < now() - interval '30 days';
```

## Good Example
```sql
SELECT drop_chunks('metrics', older_than => INTERVAL '30 days');
```

`drop_chunks` only removes chunks whose entire range falls outside the bound, so rows inside a partially-covered chunk survive. If you need those gone exactly, a DELETE is still the tool — for the boundary chunk only. Check what would go first:

```sql
SELECT chunk_name, range_start, range_end
FROM timescaledb_information.chunks
WHERE hypertable_name = 'metrics'
ORDER BY range_end;
```

For an ongoing policy rather than a one-off:

```sql
SELECT add_retention_policy('metrics', INTERVAL '30 days');
```

## Auto-fix
This rule is not auto-fixable. Translating a WHERE clause into a `drop_chunks` bound changes which rows are removed at the chunk boundary, so the substitution is not safe to make automatically.
