# MP101: warn-index-on-write-hot-table

**Severity**: Warning | **Auto-fixable**: No | **Tier**: Free (needs `--database-url`)

## What It Detects
A `CREATE INDEX` on a table that `pg_stat_user_tables` shows taking heavy write traffic — by default, more than about 50 row writes per second, or five million writes since the counters were last reset when the window is unknown.

## Why It's Dangerous
An index is not free once it is built. Every INSERT and DELETE maintains it, and an UPDATE that touches an indexed column can no longer use the heap-only-tuple path, so it writes a new index entry too. On a table that takes thousands of writes a second, that shows up as latency on the write path and as extra WAL for the replicas to replay.

The build is also at its most disruptive here. A plain `CREATE INDEX` holds a SHARE lock and blocks writes until it finishes, which on a write-hot table means blocking the busiest thing in the system. `CONCURRENTLY` avoids the block but has to keep up with everything committed while it runs, so it takes noticeably longer on exactly the tables where it matters.

## Requires Production Context
MP101 reads `n_tup_ins`, `n_tup_upd`, and `n_tup_del` from `pg_stat_user_tables`, and derives a rate from `pg_stat_database.stats_reset` when that is available. Without `--database-url` there is no traffic data and the rule stays silent.

Unlike [MP013](./MP013.md), it does not need `pg_stat_statements` — `pg_stat_user_tables` is always there. MP013 measures query volume of any kind; MP101 measures writes specifically, because writes are what an index taxes.

## Bad Example
```sql
-- events takes ~120 writes/sec in production
CREATE INDEX idx_events_type ON events (event_type);
```

## Good Example
```sql
-- Build without blocking writes, outside a transaction:
CREATE INDEX CONCURRENTLY idx_events_type ON events (event_type);
```

Then check that the index earns what it costs:

```sql
SELECT indexrelname,
       idx_scan,
       pg_size_pretty(pg_relation_size(indexrelid)) AS size
FROM pg_stat_user_indexes
WHERE relname = 'events'
ORDER BY idx_scan;
```

An index that never appears in `idx_scan` is pure write tax.

## Auto-fix
This rule is not auto-fixable. Whether the index is worth its write overhead is a judgement about your query mix. [MP001](./MP001.md) will fix the missing `CONCURRENTLY`, which is the part that is mechanical.
