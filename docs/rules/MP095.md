# MP095: warn-set-tablespace-rewrite

**Severity**: Warning | **Auto-fixable**: No | **Tier**: Free

## What It Detects
`ALTER TABLE ... SET TABLESPACE` and `ALTER INDEX ... SET TABLESPACE`.

## Why It's Dangerous
This is a physical file copy, not a catalog update. PostgreSQL reads every file belonging to the relation and writes it to the new location, holding `ACCESS EXCLUSIVE` from the first byte to the last. The table is unavailable for reads and writes the entire time, and the duration is a function of size and disk throughput — on a 500 GB table over ordinary disks, hours rather than minutes.

Disk space is the second surprise. The old files are not removed until the move commits, so both copies exist simultaneously and the destination needs the relation's full size free. A move that runs out of space partway through rolls back, having spent the whole time holding the lock.

A migration is a poor place for this because none of the controls you would want are available. There is no way to pause, resume, throttle, or observe progress, and cancelling midway discards all the work done so far and leaves the relation exactly where it started. Whatever deploy tooling is running the migration is usually holding a timeout that is far shorter than the copy.

## Bad Example
```sql
ALTER TABLE users SET TABLESPACE fast_ssd;
-- users is offline until every file has been copied
```

## Good Example
```sql
-- Planned window, bounded lock wait so it fails fast rather than
-- queueing at the head of the lock queue
SET lock_timeout = '5s';
ALTER TABLE users SET TABLESPACE fast_ssd;
RESET lock_timeout;
```

For an index, rebuilding on the target tablespace keeps the old index serving queries until the new one is ready:

```sql
CREATE INDEX CONCURRENTLY idx_users_email_new
  ON users (email) TABLESPACE fast_ssd;
DROP INDEX CONCURRENTLY idx_users_email;
ALTER INDEX idx_users_email_new RENAME TO idx_users_email;
```

Check the destination has room before starting:

```sql
SELECT pg_size_pretty(pg_total_relation_size('users'));
```

## Auto-fix
This rule is not auto-fixable. Moving storage is deliberate infrastructure work, and the safe form depends on whether the relation is a table or an index and how much downtime is acceptable.
