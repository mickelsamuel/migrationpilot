# MP003: volatile-default-table-rewrite

**Severity**: Critical (volatile default) / Warning (stable default) | **Auto-fixable**: No | **Tier**: Free

## What It Detects
`ADD COLUMN` with a `DEFAULT` built from a function PostgreSQL marks `VOLATILE` —
`gen_random_uuid()`, `random()`, `clock_timestamp()`, `timeofday()`, `nextval()`, the
`uuid-ossp` generators. The finding names the expression the migration actually wrote,
including nested cases like `floor(random() * 10)`.

The stable lookalikes — `now()`, `CURRENT_TIMESTAMP`, `statement_timestamp()`,
`transaction_timestamp()`, `txid_current()` — are reported separately, at `warning`, for a
different reason. They do not rewrite anything.

## Why It's Dangerous
Since PostgreSQL 11, `ADD COLUMN ... DEFAULT <constant>` writes the value once into
`pg_attribute.attmissingval` and touches no heap pages at all. Existing rows are given the
value on read.

A volatile default cannot take that path: by definition it must be evaluated separately for
every row. So PostgreSQL writes a fresh copy of the entire table and every index on it,
holding `ACCESS EXCLUSIVE` for the duration. Reads and writes are blocked for the whole
rewrite, and the operation needs enough free disk for a second copy of the table before it
can finish. The [ALTER TABLE manual](https://www.postgresql.org/docs/current/sql-altertable.html)
says so directly: adding a column with a volatile `DEFAULT` "will cause the entire table and
its indexes to be rewritten".

A stable default is a different problem, not a smaller version of the same one. `now()` is
evaluated once, at migration time, and every pre-existing row is given that one timestamp —
which is rarely what a `created_at` column was meant to record.

Verified on PostgreSQL 18.3 by watching `pg_class.relfilenode` and
`pg_attribute.atthasmissing` across the `ALTER`:

| Default | Rewrite | Missing value stored |
|---|---|---|
| `gen_random_uuid()`, `random()`, `clock_timestamp()`, `timeofday()`, `nextval()` | yes | no |
| `now()`, `CURRENT_TIMESTAMP`, `statement_timestamp()` | no | yes |
| a constant | no | yes |

`pg_proc.provolatile` agrees: the first group is `v`, the second `s`.

On PostgreSQL 10 and earlier there is no missing-value machinery, so any `DEFAULT` on
`ADD COLUMN` rewrites.

## Bad Example
```sql
ALTER TABLE orders ADD COLUMN public_id uuid NOT NULL DEFAULT gen_random_uuid();
-- Rewrites orders and every index on it, under ACCESS EXCLUSIVE.
```

## Good Example
```sql
-- Add the column with no default, so the catalog write is all it costs:
ALTER TABLE orders ADD COLUMN public_id uuid;

-- Fill it in batches, outside any long transaction. Repeat until 0 rows:
UPDATE orders SET public_id = gen_random_uuid()
WHERE public_id IS NULL
  AND id IN (SELECT id FROM orders WHERE public_id IS NULL LIMIT 10000);

-- Only then attach the default, for rows written from here on:
ALTER TABLE orders ALTER COLUMN public_id SET DEFAULT gen_random_uuid();
```

A constant default needs none of this — `ADD COLUMN status text DEFAULT 'pending'` is a
catalog write on PG 11+.

## Auto-fix
This rule is not auto-fixable. Splitting the column addition from the backfill changes the
migration into several statements that have to run outside one transaction, and how the
backfill should be batched depends on the table.
