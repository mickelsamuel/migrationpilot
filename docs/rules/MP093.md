# MP093: warn-default-partition-growth

**Severity**: Warning | **Auto-fixable**: No | **Tier**: Free

## What It Detects
`CREATE TABLE ... PARTITION OF ... DEFAULT` — the creation of a default partition. Bounded partitions and partitioned parent declarations are not flagged.

## Why It's Dangerous
A default partition converts a loud failure into a silent one. Without it, inserting a row that matches no partition raises an error somebody notices the same day:

```
ERROR: no partition of relation "events" found for row
```

With it, the row lands in the catch-all and nothing is logged, nothing alerts, and the missing partition goes unnoticed. That is the entire appeal — and the entire problem. Miss a month of partition creation and the default partition quietly becomes the largest table in the database, holding rows that were supposed to be spread across twelve.

Getting out is where it bites. Attaching the partition those rows should have gone to makes PostgreSQL scan the whole default partition to prove none of them overlap the new bound, under `ACCESS EXCLUSIVE` — so the cleanup is expensive in proportion to how long the problem went unnoticed. And if any row does overlap, the `ATTACH` fails outright:

```
ERROR: updated partition constraint for default partition "events_default"
       would be violated by some row
```

Now you have to move those rows out by hand before you can attach anything, while the default partition keeps growing.

The default partition is a reasonable safety net when it is monitored and kept near-empty. It is a liability when it is treated as a reason not to think about partition creation.

## Bad Example
```sql
CREATE TABLE events_default PARTITION OF events DEFAULT;
-- Silently absorbs every row with no home, forever
```

## Good Example
```sql
-- Create partitions ahead of time so a gap fails loudly instead of silently
CREATE TABLE events_2026_01 PARTITION OF events
  FOR VALUES FROM ('2026-01-01') TO ('2026-02-01');
CREATE TABLE events_2026_02 PARTITION OF events
  FOR VALUES FROM ('2026-02-01') TO ('2026-03-01');
```

If you keep a default partition, monitor it so it stays near-empty:

```sql
SELECT count(*) FROM events_default;
```

and drain it before attaching the partition its rows belong to, so the `ATTACH` scan finds nothing.

## Auto-fix
This rule is not auto-fixable. Whether a default partition is right for your table is a design decision, and the alternative — automated partition creation, via `pg_partman` or a scheduled job — is infrastructure rather than a change to this statement.
