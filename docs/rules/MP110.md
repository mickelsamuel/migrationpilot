# MP110: warn-partitioned-parent-fanout

**Severity**: Warning | **Auto-fixable**: No | **Tier**: Free (needs `--database-url`)

## What It Detects
`ALTER TABLE` or a plain `CREATE INDEX` on a natively partitioned parent that has 20 or more partitions in production.

## Why It's Dangerous
DDL on a partitioned table recurses. PostgreSQL locks the parent and every partition, and holds all of those locks until the statement commits. Two consequences follow from that.

The blocking window is set by the slowest partition, not by the statement. A `lock_timeout` helps only if it fires before the queue behind the parent lock has stalled everything else — and by the time you are waiting on partition 300, plenty is already queued.

And the lock count scales with the partition count. On a table with a partition per day and a couple of years of history, a single ALTER can run into `max_locks_per_transaction`, which fails the statement outright.

`CREATE INDEX CONCURRENTLY` is not part of this: PostgreSQL does not support concurrent builds on partitioned tables at all, so the statement never reaches this rule.

## Requires Production Context
Nothing in the migration file says how many partitions a table has, and that count is the whole finding. MigrationPilot reads `relkind` and a count from `pg_inherits`; without `--database-url` the rule stays silent.

Extension-managed parents are skipped: a TimescaleDB hypertable gets [MP105](./MP105.md) and a pg_partman parent gets [MP108](./MP108.md), both of which say something more specific than this rule can.

## Bad Example
```sql
-- events is partitioned by day, 365 partitions live
ALTER TABLE events ADD COLUMN note text;
```

## Good Example
```sql
-- Confirm the fan-out and that the lock table can hold it:
SELECT count(*) AS partitions FROM pg_inherits WHERE inhparent = 'events'::regclass;
SHOW max_locks_per_transaction;

-- Fail fast instead of stalling every query queued behind the parent lock:
SET lock_timeout = '5s';
ALTER TABLE events ADD COLUMN note text;
RESET lock_timeout;
```

For an index, build per partition first and attach afterwards. Each concurrent build blocks only its own partition, and creating the parent index over ready-made partition indexes is a metadata-only operation:

```sql
CREATE INDEX CONCURRENTLY idx_events_note_p1 ON events_p1 (note);
CREATE INDEX CONCURRENTLY idx_events_note_p2 ON events_p2 (note);
-- ... one per partition ...

CREATE INDEX idx_events_note ON ONLY events (note);
ALTER INDEX idx_events_note ATTACH PARTITION idx_events_note_p1;
ALTER INDEX idx_events_note ATTACH PARTITION idx_events_note_p2;
```

The parent index stays invalid until every partition has a matching index attached.

## Auto-fix
This rule is not auto-fixable. Expanding one statement into a per-partition sequence needs the partition names, which only exist in production.
