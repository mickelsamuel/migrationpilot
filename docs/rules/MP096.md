# MP096: warn-matview-with-data

**Severity**: Warning | **Auto-fixable**: No | **Tier**: Free

## What It Detects
`CREATE MATERIALIZED VIEW` that populates on creation — either written as `WITH DATA` or, far more often, written with nothing at all, since `WITH DATA` is the default. `CREATE TABLE ... AS` shares the same parse node and is not flagged.

## Why It's Dangerous
Because it is the default, this usually happens without anyone choosing it. The statement looks like a definition and behaves like a batch job: the migration runs the view's query to completion before returning, holding locks on every table the query reads for the whole build. A materialized view is generally a materialized view because the query is expensive, so the build is expensive by construction — an aggregate over a large fact table can take many minutes.

For that whole time the migration transaction stays open, which extends every lock it already holds and keeps `xmin` pinned so vacuum cannot clean up rows anywhere in the database. Deploy tooling with a timeout gives up partway and leaves the schema half-applied.

`WITH NO DATA` separates the two decisions. Creating the view becomes instant, and the expensive part becomes a `REFRESH` you can schedule, retry, and run outside the deploy. The tradeoff is real and worth stating. An unpopulated matview cannot be queried at all:

```
ERROR: materialized view "daily_revenue" has not been populated
```

and the first `REFRESH` cannot use `CONCURRENTLY` — `ERROR: CONCURRENTLY cannot be used when the materialized view is not populated`. So the refresh has to happen before anything depends on the view, and the ordering matters.

## Bad Example
```sql
CREATE MATERIALIZED VIEW daily_revenue AS
  SELECT date_trunc('day', created_at) AS day, sum(total)
  FROM orders GROUP BY 1;
-- Migration blocks until the aggregate finishes
```

## Good Example
```sql
-- Returns immediately
CREATE MATERIALIZED VIEW daily_revenue AS
  SELECT date_trunc('day', created_at) AS day, sum(total)
  FROM orders GROUP BY 1
  WITH NO DATA;
```

```sql
-- Outside the migration. First refresh cannot be CONCURRENTLY,
-- and the view is not queryable until it completes.
REFRESH MATERIALIZED VIEW daily_revenue;

-- A unique index lets every later refresh run without blocking readers
CREATE UNIQUE INDEX CONCURRENTLY daily_revenue_day ON daily_revenue (day);
REFRESH MATERIALIZED VIEW CONCURRENTLY daily_revenue;
```

## Auto-fix
This rule is not auto-fixable. Appending `WITH NO DATA` is mechanically easy and semantically significant: it leaves the view unreadable until something refreshes it, so it needs a corresponding change to whatever runs next.
